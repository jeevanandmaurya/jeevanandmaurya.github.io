Multi-threaded Rapier physics in the browser

Rapier already has a parallel solver. The official JS builds just compile it out. Turning it on with WebAssembly threads gives 2–3.5× faster physics steps on large scenes, with identical results.

The problem: one core, one frame budget

I was optimizing physics for browser games and built a benchmark harness: five scenes (box pyramids, a pile of 3,136 mixed shapes, 8,000 spheres, jointed chains, props on a triangle-mesh terrain), run identically in Rapier native (Rust) and in rapier.js (WebAssembly).

The phase breakdown showed where the time goes. Collision detection costs about the same in WASM as natively. The gap is almost all in the constraint solver, and the official JS builds run it on a single thread, while a desktop CPU has 6 to 16 cores. At 60 FPS you get 16.7 ms per frame for everything. A 3,000-body pile took 15 ms of physics alone, and spikes went past 30 ms.

The surprise: the feature already exists

Rapier's Rust crate has a parallel feature. It runs broad phase, narrow phase, the constraint-graph colouring, the solver and integration on a rayon thread pool. Native apps use it. The official npm packages are simply compiled without it, because threads on the web come with conditions:

  • WebAssembly memory must be a SharedArrayBuffer, which browsers only allow on cross-origin-isolated pages (the COOP/COEP headers).
  • Rust's standard library has to be rebuilt with atomics (-Z build-std, nightly Rust).
  • rayon needs threads, and on the web those are Web Workers. wasm-bindgen-rayon turns a pool of workers into rayon's global pool, all sharing one WASM memory.
  • world.step() now blocks while it waits for its threads, and browsers forbid blocking the main thread, so physics has to run in a Worker.

None of that touches the physics. So I didn't fork the engine; I changed how it's compiled.

How the build works

  1. Check out the exact upstream commit an official npm release was built from (npm records it as gitHead).
  2. Run upstream's own build generator for its SIMD variant.
  3. Make three additive edits to the generated crate: enable parallel + unsync-callbacks, add wasm-bindgen-rayon, and export initThreadPool.
  4. Compile with +atomics,+bulk-memory,+simd128, shared memory, and build-std.
  5. Use upstream's TypeScript API unchanged, except init(), which also starts the thread pool.
Why unsync-callbacks? JavaScript physics hooks and event handlers hold JS objects, which aren't thread-safe. Rapier's own unsync-callbacks mode hands worker threads a no-op hook and processes any collider pair with user hooks on the calling thread only. JS callbacks stay correct (tested: 171,007 hook calls, identical to the official build); only hooked pairs lose parallelism.

Two traps I hit: upstream's release profile has strip = true, which deletes the section wasm-bindgen uses to detect threads (it would silently ship a non-threaded build); and Vite rewrites served JS in ways that break the blob-URL workers wasm-bindgen-rayon spawns. The package ships a small Vite plugin for that.

Is it the same physics?

Yes. Every run compares the threads build against the official @dimforge/rapier3d-simd-compat of the same version, on a scene that uses the full API: 2,540 bodies, a 40-link joint chain, a sensor, collision events, JS contact-filter hooks, raycasts and shape queries.

Staying in sync with upstream automatically

Because nothing upstream is patched, new releases don't conflict. A daily GitHub Action checks npm; when Dimforge publishes a release, it pins the exact commit, builds, runs the browser test suite against the official package of the same version, and publishes with npm provenance. Every assumption about upstream's layout is asserted, so if upstream changes something the build depends on, it stops with a clear message and opens an issue instead of shipping a broken package.

Using it

npm i @jeevanand/rapier3d-threads
// physics.worker.js
import RAPIER from "@jeevanand/rapier3d-threads";
await RAPIER.init({ threads: 4 }); // default: hardwareConcurrency / 2
const world = new RAPIER.World({ x: 0, y: -9.81, z: 0 });
// … the usual Rapier API …
world.step();

Serve the page with Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (on static hosts like GitHub Pages, the community coi-serviceworker adds them; this blog's demo uses it). Fall back to the official package when crossOriginIsolated is false: the API is identical.

When it's worth it

  • Yes: thousands of active bodies, big piles and stacks, destruction, crowds, open worlds where one world doesn't fit the frame budget.
  • Less so: small scenes (a 1,200-body chain only went 2.7 → 1.4 ms), pages that can't be cross-origin isolated (some ads/embeds/portals), or apps that must call step() on the main thread.
  • Thread count matters: on a 6-core/12-thread laptop, 6 threads beat 12. The default is half of hardwareConcurrency.
